# ARCHITECTURE.md — North Bridge PCs Website Rebuild

## Stack

Static HTML/CSS/vanilla JS. No framework, no client-side build step required
to *run* the site. GitHub Pages hosting — no backend, no database, no
server-side form processing (forms go through FormSubmit, same as before).

A **local build script** (`build-tools/stitch.py`) is used to assemble
shared header/footer/nav partials into final static HTML files before
committing — see "Why a build script" below. This runs on your machine
before you push, not in the browser. The output is still plain static HTML.

## Why this structure (vs. the old site)

The old site worked, but had two maintainability problems worth fixing:

1. **Header/footer/nav were copy-pasted into all 8 HTML files.** A nav
   change meant editing 8 files by hand and risking them drifting out of
   sync (they'd already started to slightly — the mobile-nav markup wasn't
   always byte-identical to desktop nav across pages).
2. **Data and rendering logic lived in the same file** (`builds.js` mixed
   the PC array with the HTML-generating functions). Fine at 3 PCs, harder
   to reason about as it grows.

This rebuild separates those concerns:

- **`js/data/*`** is the only place you should need to touch for routine
  updates — new PC, price change, toggling a feature on, adding a
  testimonial.
- **`js/render/*`** contains the functions that turn that data into HTML.
  You shouldn't need to touch this for content updates, only for design
  changes.
- **`js/partials/*` + `stitch.py`** solves the header/footer duplication
  without adding a client-side framework or a runtime fetch() for the nav
  (which would flash an unstyled page and hurt SEO crawlability).

### Why a build script instead of just living with the duplication

Alternatives considered:

- **Keep copy-pasting the nav into every file** (status quo): simplest,
  but the exact problem being fixed.
- **Client-side JS include** (`fetch('header.html')` on page load): no
  build step needed, but causes a visible flash of missing nav on slow
  connections, and search engines / social-media link previews that don't
  execute JS would see a page with no navigation.
- **A local static-site generator** (Eleventy, Hugo, etc.): solves this
  properly but is a real dependency with its own learning curve and
  config — more than this project needs.
- **A small custom Python script that stitches partials at commit time**
  (chosen): zero runtime cost, output is identical to hand-written static
  HTML, no new dependency beyond Python (which is already part of your
  workflow), and it's simple enough to read top-to-bottom in a couple of
  minutes if you ever need to change it.

You'll run `python3 build-tools/stitch.py` before committing, the same way
you'd run a linter — it injects `js/partials/header.html`,
`js/partials/footer.html`, and `js/partials/analytics.html` into each page
template via marker comments (`<!--HEADER:id-->`, `<!--FOOTER-->`,
`<!--ANALYTICS-->`), plus a separate `<!--SEO-->` marker it builds
canonical/OG/structured-data tags for directly. See docs-archive/DECISIONS.md for the
history of each addition. The script also writes `sitemap.xml` and
`robots.txt` (404.html is left out of the sitemap) from `SITE.url` in
`js/data/config.js`.

## Feature toggle philosophy

One config module (`js/data/config.js`) holds every feature's on/off state
plus whatever data that feature needs (a phone number, a social URL). Pages
check `config.features.X.show` before rendering anything related to X.
Turning a feature on is: flip the boolean, fill in the value, done — no
HTML hunting.

## PC data model

The old model stored `title: "Ryzen 5 3600 / RTX 2070 Super"` as one string
and only broke out `ram` and `storage` separately. The new model gives each
component its own field (`cpu`, `gpu`, `motherboard`, `ram`, `storage`,
`psu`, `case`, `cooler`, `os`, `networking`, `accessories`), each optional —
missing fields are simply omitted from display rather than showing an empty
row. This matches the "complete build card" system described in the
project brief: a normal buyer still sees a clean summary, but every field
is available for someone who wants the full spec sheet.

**Source of truth (B-084):** each PC is `content/builds/<id>.json` (price a number, parts as plain strings, photos as paths).
`build-tools/content.py` validates them and writes `js/data/builds.js` (the exact shape above; price formatted as `$650`) and
`gallery.js`. Only `available` and `sold` listings are written, so Draft/Hidden listings have no public page. The page scripts
still render in the browser; every piece of listing text goes through `escapeHtml()` (`js/render/escape.js`).

Media is a `{ images: [], videos: [] }` object per build (and, later, per
component) rather than a flat `photos` array, so a listing can have any
combination of photos/video without special-casing.

## Remote admin and publishing (B-084)
Pages CMS (hosted, free; `.pages.yml`) edits `content/` and `images/` in the GitHub repository. Every push to `main` runs
`.github/workflows/publish.yml`: `photos.py` (cleans photos), `content.py` (checks and generates data), `stitch.py`, then it saves
changed generated files back to the repository (`ci-build.sh`, retries if someone saved meanwhile) and deploys only the public files
(`assemble-site.sh`: no scripts, docs or content sources) to GitHub Pages. A failed check stops before deploy, so the live site keeps
its last good version. Setup and use: ADMIN_SETUP.md. Not covered yet: video clips in the form, backups, failure email (Phase 2).

## Event/promo system

Replaces the old single hardcoded `EVENT` object with an array of events,
each with its own date range, banner copy, and a `showCountdown` flag.
Rationale: the project brief flags countdown timers as a manipulative
pattern to avoid, but the old site's Back to School sale was a real,
non-fake deadline — the tension isn't really "countdown vs. no countdown,"
it's "does this specific promotion warrant urgency framing." Making it a
per-event choice lets a clearance sale skip the countdown while a genuine
23-hour flash deal could use one, without hardcoding a site-wide stance
either way. (Flagged for confirmation — see docs-archive/PROJECT_STATUS.md.)

## Theming

**Where the live theme comes from.** `css/tokens.css` defines the original
design tokens (`--bg`, `--card`, `--accent`, `--text`, `--border`, ...) as a
single dark set (it used to have a `@media (prefers-color-scheme: light)`
override block too; removed in A-022). Those color values are the pre-redesign blue palette and are no longer what
visitors see. `css/theme.css` is loaded after it on every page and redefines
the same custom properties in its own `:root` block, so every component that
reads a token (`style.css`, `build-detail.css`, `part-boxes.css`, ...)
picks up the redesign without edits. The page-specific stylesheets sit between
`style.css` and `theme.css` in the `<link>` order; `theme.css` is always last.

**Dark only.** The site has no light mode, and the light and dark views are
identical (owner decision, A-022). `theme.css` redefines the tokens
unconditionally (outside any media query) and sets `color-scheme: dark`;
`tokens.css` also has a single dark palette and `color-scheme: dark`. The
leftover `@media (prefers-color-scheme: light)` block in `tokens.css` was
removed in A-022: `theme.css` already overrode every token in it except
`--success`, so its only visible effect was a different green (`#16a34a`
vs `#22c55e`) on the "available" badge, event price and event badge for
visitors whose system was set to light (those only render for an available
listing). `--success` itself is still used and still defined, once, in
`tokens.css`. Checked by emulating light and dark on all 9 pages: identical.
There is no JS theme switcher.

**Current token values** (all in the `:root` block of `css/theme.css`; read the
file for exact values, the ones that matter for understanding the design are):
- Accent is **"Cask"**, `--accent` = `#8b3f5e`, chosen in
  VISUAL_REDESIGN.md decision 14. Solid accent fills (`.btn-primary`,
  `.back-to-top`, `.nav-cta`, `.skip-link`) use white text.
- `--accent-text` (`#ae798e`, a lightened tint) is the token for accent-colored
  text, borders, outlines and icons, because the base value is too dark to read
  as a thin line or small text. Use `--accent` only as a solid fill.
- `--accent-h` was removed in A-040 (it equalled `--accent`); `--accent-h2` is defined but
  unused. Button hover brightens the same fill (`filter: brightness(1.12)`)
  rather than switching to a second color (decision 9).
- `--border-field` (`#6a665e`) is the resting border for form fields, added in
  A-012 so fields reach 3:1 contrast against the card; `--border` is for
  decorative dividers only.
- Surfaces and text are a warm near-black palette (`--bg` `#0c0c0e`, `--card`
  `#17171a`, `--text` `#f2efe9`). Shadows are neutral (`--shadow`,
  `--shadow-lg`), not colored.
- Fonts: `theme.css` loads three Google Fonts with an `@import` (the only
  place fonts are loaded): Bricolage Grotesque for headings
  (`--font-heading`), Manrope for body text (`--font-body`), Space Mono for
  technical data such as prices, spec values and budget tables
  (`--font-mono`). Each has a system-font fallback stack.

**Rules of thumb when editing CSS** (all recorded in code comments and
VISUAL_REDESIGN.md):
- Use tokens, not raw colors. Hardcoded colors do not follow a theme change; the
  redesign had to sweep leftover amber and blue `rgba(...)` literals for this
  reason (decision 14).
- `theme.css` wins the cascade because it loads last. When a rule in another
  stylesheet seems to have no effect, check `theme.css` for an override of the
  same selector. (A stale override block there likely defeated
  build-detail decisions 7 and 8 until it was removed; see decision 14.)
- A visual change belongs to the visual-redesign process (VISUAL_REDESIGN.md,
  one decision at a time, owner-approved), not to routine content updates.

## Visual redesign history

The site's visual language has been redesigned twice on top of the architecture
above. Neither changed the HTML/JS structure described elsewhere in this file.

1. **"Forge" (dark/amber), now superseded.** Done in two batches (homepage
   first, scoped to `body.theme-forge` in `css/homepage-forge.css`; then the
   other pages in one pass, when the file became `css/theme.css` and was
   unscoped). A full-site QA/visual audit followed (D27). That scoping class
   and the old filename no longer exist; the history is in
   docs-archive/DECISIONS.md (D22-D24, D27) and docs-archive/PROJECT_STATUS.md.
   `js/render/trustSection.js` was rewritten during Batch 2 into the shared
   `renderTrustEvidence()` used by the homepage and `build.html`.
2. **Visual reconsideration, in progress.** A one-decision-at-a-time process
   (owner approves each decision from real rendered options) that replaced
   amber with the "Cask" accent and reworked individual components: buttons,
   typography, section headers, build cards, form fields, success states,
   the contact situation picker and more. The authoritative, current record is
   **VISUAL_REDESIGN.md**; START_HERE.md "Current state" says which pages are
   done. Every page has now been walked at desktop width (A-030); the mobile and tablet
   pass is still to do.
